The operator's opencode carried a plugin: ~/.config/opencode/plugins/opencode-loop.ts, a bundled build ("legacy-v1", 4143 lines) that registers goal tools (opencode_loop_goal_complete|blocked|progress), rewrites commands at command.execute.before, survives compaction via experimental.session.compacting, watches event for command.executed, drives continuations through the SDK's session command surface, and guards itself with a max-no-progress counter. It is the opencode-loop way of working with zero host references: its goals, progress, and completion live in its own state, unreceipted and ungoverned. The host doors (/host-goal, /host-tasks, /host-ci) are one-shot injections with no loop. The retired references (the legacy bundle, the community goal plugins, ByBrawe's completion machinery) each hold a piece; none holds the discipline. This milestone builds the piece that does: the loop as a host surface.

The rulings

  1. The host verifier stack is the sole verifier. ByBrawe's completion pipeline, independent verifier session, and contract format are retired as reference: they do not combine with the ladder (the verify gate, the obligations and allium specs, the kani rungs, the ci receipts, the prose lane, the refs walk, book --check, software --check, and the composed closure gate), and a second, weaker verifier beside a complete one is the defect the house exists to refuse.
  2. Fully host-idiomatic. Not a translation: the command set is the host verb family, the tracked surfaces are the only state authority, and the plugin adds no vocabulary an agent has not already met in the doors and the verbs.
  3. V2-native only. Built against the OpenCode 2 plugin API (Plugin.define, the native plugins config, the native hooks). The installed opencode is 1.18.21 with @opencode-ai/plugin 1.17.12 (the V1 generation), which cannot load it; the harness's live tiers run on an OpenCode 2.x binary pinned into a scratch directory that never touches the daily install, or wait for the operator's upgrade; the build node records which.
  4. The legacy plugin retires immediately. Learnings recorded below; the bytes stay on disk under a retired name until the swap.
  5. The V2 lifecycle and its autonomous coordinator are the continuation owners (operator ruling, mid-cut): the plugin registers as the coordinator's client on OpenCode 2's V2 lifecycle (native prompt admission, the durable inbox, session-idle recovery); it never hand-rolls a competing loop, which is what makes one controller per session structural rather than promised.

The design: the loop as a host surface

One state authority: the tracked surfaces

GOAL.md and the receipt fold are the switch. An active unparked goal arms the loop; a parked goal holds it; no goal silences it; a completed surface stops it. The plugin holds no persistent state at all, only an in-memory iteration count and the last emission; a session restart forgets nothing that matters, and a cold read reconstructs everything from the surfaces. The Orin and Bly verdicts (reconstructible state, the version seam) are met structurally, not by discipline.

The command set is the host verb family

  • /host-goal (orient; the existing door, with the goal show emission injected verbatim)
  • /host-goal set <plan/NNNN> (declare; free text refused to goal propose per call/0061: a goal IS a milestone, and the audited declaration is the authority)
  • /host-goal park <reason> and /host-goal unpark (the hold and the resume ARE the host verbs; the reason rides the receipt and the frontier reads held)
  • /host-goal complete (the operator's typed command runs the operator's composed gate)
  • /host-tasks (the frontier; the existing door) and /host-ci (the lanes; the existing door)

Nothing else: no contract, audit, budget, doctor, queue, history, edit, or restore. Each is either a projection the emission already carries or a host act the CLI owns. The model-facing surface is the same three tools the doors direct: goal_show and tasks_status (read) and tasks_record (the write the doors already direct). No model-facing complete tool; the legacy plugin's opencode_loop_goal_complete is the named anti-pattern, and completion is never model-claimable: the loop stops when the tracked surface says complete, and only goal complete, operator-invoked, writes that surface.

The loop and its bounds

On session idle with an armed goal, the continuation body is the goal show emission plus the door doctrine: work the NEXT line; if it is a command, run it as printed; if it says work a task, start it; never invent a command or a flag; NEEDS YOU non-none means ask the operator and nothing else runs. The emission is the prompt; nothing is referenced but absent. Bounds, each printing its stop reason: the iteration cap (default 25, HOST_LOOP_MAX_ITERATIONS, unknown values fail closed), three consecutive turns with no receipt and no frontier movement (counted mechanically, never assessed, Wren's verdict), a no-tool-call turn, a verb refusal, NEEDS YOU, parked, complete. Resuming after any stop is the operator's hand: a new user turn or an unpark. One controller per session by construction: the single plugin owns the loop, so the two-controller hazard the references document never arises.

Zero new verification

The plugin adds no checks, no digests, no verifier session, no second contract format. The ladder already runs; the loop's only job is to keep the agent on the NEXT line until the ladder or the operator speaks. Every autonomous action lands in a receipt, so the ledger is the audit trail of an unattended session, and the operator's surfaces (the emission, the receipts, the lanes) are the trust surface, never a chat claim.

The retirement and its learnings

The legacy bundle retires immediately by ruling; the bytes stay on disk under a retired name until the swap. Learnings taken before removal:

  • The live-proven V1 surfaces (tool registration, command.execute.before, event, experimental.session.compacting, the SDK session-command surface), all on opencode 1.18.21 with @opencode-ai/plugin 1.17.12; the V2 gap this ruling accepts is recorded at discovery.
  • The no-progress counter (three turns), which the loop adopts mechanically: receipt stanzas and frontier movement are counted, never assessed.
  • The two continuation registers (a goal-mode and a loop-mode prompt), which the A/B arms inherit as variants.
  • The cost that justified retirement: an unreviewable bundle governing an unreviewable loop, with state the host ledgers never saw.

From the community set, also retired as references: conservative continuation (a turn with no tool calls stops the loop; adopted), the budget concept (becomes the iteration cap), and evidence-mapped completion (the composed gates are the stronger form).
